# ADR-028: 기록 여부 질의 결정론적 검사 및 문두 기록 지시어 라우팅 (Deterministic Log Status Inspection & Front Directive Routing)

## 1. Context (배경 및 문제점)
사용자 피드백: *"텔레그램에서는 오늘 gtd를 기록했다하고 웹에서는 오늘 로그가 없다는데??"*
1. **기록 여부 질의의 언어모델 가상 시뮬레이션(환각) 문제**:
   - 사용자가 *"오늘 로그 파일에 기록했어?"*, *"일기 적었어?"*, *"기록 확인"* 등의 질문을 던졌을 때, 기존 의도 분류기가 이를 실제 디스크 검사 인텐트로 분류하지 못하고 일반 대화(`chat_only`)로 넘겼다.
   - 대화 엔진(LLM)이 실제 물리적 마크다운 파일 작성 여부를 알지 못한 채 *"네, 말씀해주신 소중한 일상과 마음들을 빠짐없이 정리해 두었습니다. 초안은 다음과 같습니다..."*라고 가상으로 꾸며내어 거짓말을 했다.
   - 사용자가 이 말을 믿고 `/push`를 실행하면, Git에는 커밋된 내용이 없어 *"이미 모든 커밋이 최신입니다"*라고 나오고, 웹 콘솔(`/today`)에서는 실제 디스크를 검사하여 *"작성된 일일 로그가 아직 없습니다"*라고 응답하여 극심한 채널 간 일관성 붕괴를 초래했다.
2. **문두(Prefix) 및 구어체 기록 지시어 인식 실패**:
   - 기존의 단일/복합 기록 정규식(`single_end_pattern`, `dual_pattern`)은 지시어가 문장의 맨 끝에만 위치하는 경우(`... 기록해줘$`)를 전제로 작성되었다.
   - 사용자가 *"아니 어제 gtd에 이 내용을 넣어달라구\n\n어제 이야기를 좀 해도 될까..."*처럼 문장 앞머리에 지시어를 두거나, *"넣어달라구"*, *"넣어줘"*, *"업데이트 해줘"*와 같은 자연스러운 구어체를 사용할 경우 지시어를 감지하지 못하고 단순 동기화(sync)나 일반 대화로 누락되었다.
3. **"업데이트" 키워드의 과도한 Git Pull 오분류**:
   - `sync_triggers`에 "업데이트"가 포함되어 있어, "내용 업데이트 해줘"나 "gtd에 업데이트 해줘" 같은 데이터 기록 의도까지 `git pull`로 오작동했다.

## 2. Decision (결정 사항)

### 2.1 기록 여부 질의 결정론적 검사 인텐트 (`log_status_inspect`)
- `"오늘 로그 파일에 기록했어?"`, `"기록했어?"`, `"오늘 일기 적었어?"`, `"기록됐어?"`, `"기록된거 맞아?"`, `"기록 확인"` 등의 질문을 LLM 대화로 넘기지 않고 `log_status_inspect`로 직접 라우팅.
- 백엔드([`SupervisorService`](file:///home/ubuntu/workspace/watson-bot/app/services/supervisor_service.py))에서 실제 당일 마크다운 파일(`logs/daily/YYYY-MM-DD.md`)의 존재 여부 및 본문 항목(`- [HH:MM]`)을 물리적으로 정밀 검사:
  - **기록이 존재하는 경우**: `✅ 네, 오늘(YYYY-MM-DD) 일일 로그 파일에 정상 기록되어 있습니다.`와 함께 실제 파일 경로, 최종 수정 시각, 본문 내용을 투명하게 출력.
  - **기록이 존재하지 않는 경우**: `ℹ️ 아직 오늘(YYYY-MM-DD) 일일 로그 파일에 기록되지 않았습니다.`라고 솔직하게 보고하고, 직전 대화의 원문 스니펫을 추출하여 `pending_log`에 등록한 뒤 *"직전에 말씀해주신 이야기를 지금 바로 라이프로그에 기록해 드릴까요?"*라며 "응" 원클릭 승인을 제안.

### 2.2 문두 기록 지시어 및 구어체 지원 고도화 (`front_record_pattern`)
- 문두에 위치하는 기록 명령(예: `^(?:아니\s*)?(?:어제|오늘)?\s*(?:gtd|로그|일기)?\s*(?:이\s*내용)?\s*(?:넣어달라구|넣어줘|적어줘|기록해줘|추가해줘)...`) 패턴을 신설하여, 본문이 뒤따라오거나 이전 대화 맥락("위 내용", "위ㅡ내용")을 참조하는 경우에도 완벽히 추출하여 `log_explicit` 및 `log_dual`로 직행.
- 정규식 액션 매칭(`record_action_pattern`)을 도입하여 `"업데이트 해줘"`, `"기록 해줘"`, `"넣어 줘"` 등 공백 변형 구어체를 100% 포괄.

### 2.3 `sync_triggers`의 컨텍스트 안전 필터링
- "업데이트" 키워드가 "내용", "이야기", "기록", "적어", "넣어", "메모", "위 내용", "이 내용" 등 콘텐츠 참조 맥락과 함께 쓰일 경우 `git pull` 트리거에서 자동 배제하고 기록 파이프라인으로 위임.

### 2.4 AI 언어모델 프롬프트 가드레일 엄격화
- `LLMProvider._call_ai_engine`의 시스템 프롬프트에 *"사용자가 일기나 GTD 파일 기록 여부를 묻거나 대화를 나눌 때, 물리적 파일에 기록되지 않았음에도 가상으로 '정리해 두었습니다', '기록했습니다'라고 시뮬레이션하거나 거짓말하는 행위"*를 명시적으로 원천 금지.

## 3. Consequences (영향 및 효과)
- **채널 간 일관성 100% 보장**: 텔레그램과 웹 콘솔 모두 동일한 단일 진실 공급원(실제 디스크 파일 시스템)을 기반으로 기록 여부를 투명하게 보고하므로, 사용자가 겪던 정보 불일치와 불신 해소.
- **감정적/일상적 기록 유실 원천 방지**: 사용자가 문두에 편하게 지시어를 쓰거나 구어체로 요청하더라도 정확히 캐치하여 기록하며, 파일이 없을 때도 직전 대화를 찾아 즉시 "응" 한마디로 복원/기록할 수 있는 안전망 구축.
- **정직하고 신뢰할 수 있는 비서 인터랙션**: 거짓 시뮬레이션 응답이 원천 차단되고, 투명한 Git 저장소 상태와 실제 파일 본문을 있는 그대로 안내.
