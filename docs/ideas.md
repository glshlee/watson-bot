## 1. 🌟 선정된 4대 핵심 개발 아이디어

### 아이디어 1: [회고 & 탐색] 과거 라이프로그·GTD 검색 & 주간 결산 리포트
> **"내가 지난달 서산 갔을 때 어디 갔었지?", "지난주에 그 에러 어떻게 해결했더라?", "이번 주엔 운동을 며칠이나 했지?"**

#### 1) 배경 및 필요성
* 일일 로그(`logs/daily/YYYY-MM-DD.md`)가 쌓여가지만, 현재는 **당일 기록과 GTD 현황** 위주로만 열람할 수 있습니다.
* 기록의 진정한 효용은 **필요한 순간 과거의 생각과 해결책을 즉시 찾아내고(Search)**, **한 주간의 삶을 돌아보며 정서적·행동적 피드백(Weekly Review)을 얻는 것**에 있습니다.

#### 2) 주요 기능 명세
* **자연어 및 키워드 로그 검색 (`/search [키워드]` or "지난달 서산 맛집 찾아줘")**:
  * 일일 로그 디렉토리(`logs/daily/`) 및 GTD 파일 전체를 대상으로 빠른 텍스트/시맨틱 검색.
  * 검색 결과는 **날짜, 일치된 섹션, 본문 하이라이트 스니펫**이 포함된 카드 형태로 텔레그램 및 웹 콘솔에 브리핑.
* **주간 결산 회고 자동 브리핑 (`/weekly`, 매주 일요일 21:00 KST 푸시)**:
  * 지난 7일간 완료한 GTD 태스크(`## ✅ 오늘 완료한 일`) 전수 집계 및 통계(총 N개 완료).
  * 카테고리별 활동 일수(운동 N일, 독서/학습 N일, 업무 집중 N일) 시각화.
  * AI가 한 주간의 일기를 종합 분석하여 따뜻한 총평과 다음 주를 위한 격려 메시지 생성.
* **장기 체류 수집함(Inbox) 정리 가이드**:
  * 2주 이상 Inbox에 머물러 있는 과제들을 선별하여 "이 태스크는 삭제할까요, 아니면 Next Actions로 옮길까요?" 제안.

#### 3) 기술 아키텍처 설계
* `SearchService`:
  * 파일 I/O 기반 고속 정규식 검색 엔진 또는 SQLite `FTS5` 가상 테이블을 활용한 전체 텍스트 검색(Full-Text Search) 인덱싱.
  * 날짜 범위 필터링(`from_date`, `to_date`) 및 카테고리 태그 매칭.
* `WeeklyReviewService`:
  * 지난 7일간의 `YYYY-MM-DD.md` 파일을 파싱하여 정량 데이터(완료 태스크, 시간대별 활동) 추출.
  * `LLMProvider`를 통해 주간 회고 요약문 합성.

### 아이디어 2: [멀티모달 시각 지능] 사진·영수증·운동인증 Vision AI 분석 & 스마트 기록
> **"식당 음식 사진이나 애플워치 운동 결과 화면을 텔레그램으로 툭 던지면, 알아서 분석해 예쁜 일기로 저장"**

#### 1) 배경 및 필요성
* 현재 텔레그램으로 사진을 전송하면 파일 저장 후 단순 마크다운 링크(`![photo](...)`)로만 남습니다.
* 스마트폰에서 가장 자연스러운 일상 캡처 방식은 **사진 촬영**입니다. 사진 속 정보(OCR, 운동 수치, 영수증 금액, 음식명)를 AI가 이해하고 기록 양식으로 정제하면 입력 허들이 획기적으로 낮아집니다.

#### 2) 주요 기능 명세
* **Gemini Flash Vision 기반 멀티모달 시각 분석**:
  * 사진 수신 시 Gemini Vision API를 호출하여 이미지의 유형과 텍스트(OCR), 시각적 특징 자동 추출.
* **도메인별 특화 파싱 및 자동 템플릿 서식화**:
  * 🏃 **운동 인증샷 (애플워치, 가민, 헬스장 인바디, 러닝 앱 화면)**:
    * 운동 종목(러닝, 웨이트, 사이클), 심박수, 칼로리(kcal), 운동 시간, 거리(km)를 추출하여 `## 🏃 운동 & 건강` 섹션에 정갈한 표/불릿으로 기록.
  * 🍲 **식사 & 맛집 사진**:
    * 메뉴명, 음식 종류, 식사 분위기를 분석하여 맛집 탐방 저널 초안 제안.
  * 🧾 **영수증 및 지출 영수증**:
    * 상호명, 결제 일시, 총 결제 금액, 주요 구매 항목을 추출하여 가계부 기록 또는 GTD 구매 확인 태스크 생성. (카드번호 등 민감 정보 자동 마스킹)
  * 📝 **화이트보드 / 포스트잇 메모 사진**:
    * 손글씨 OCR을 통해 텍스트로 디지털화하여 GTD 수집함(`inbox.md`)에 액션 태스크로 자동 안착.
* **2단계 사전 검토 카드 연계**:
  * 분석된 결과를 즉시 커밋하지 않고, "이런 내용으로 기록할까요?" 초안 카드를 제시하여 `[✅ 응, 기록해줘]` 승인 후 커밋.

#### 3) 기술 아키텍처 설계
* `VisionService`:
  * 텔레그램 `photo` 다운로드 ➔ 이미지 리사이즈/압축 ➔ Gemini Vision API 멀티모달 프롬프트 전송.
  * 결과 JSON 구조화 파싱 (`category`, `summary`, `metrics`, `markdown_block`).

### 아이디어 3: [GTD 완결성] 마감일(Due Date / D-Day) 자동 감지 & 브리핑 알림 시스템
> **"`- [ ] 세무 신고 ~2026-09-20` 마감일이 다가오면 아침 브리핑에 D-Day 경고와 함께 최상단 배치"**

#### 1) 배경 및 필요성
* 현재 GTD 태스크는 단순히 대기 목록(`- [ ]`) 형태로 관리되어, 특정 일자까지 완료해야 하는 마감일(Due Date) 추적과 긴급도 판별이 어렵습니다.
* 비서가 마감일을 스스로 계산하여 D-Day 알림을 주어야 중요한 일정 누락을 원천 방지할 수 있습니다.

#### 2) 주요 기능 명세
* **유연한 마감일 표기법 자동 인식**:
  * `- [ ] 자동차 정기검사 예약 ~2026-09-20` (틸드 표기)
  * `- [ ] 분기 보고서 제출 @due(2026-09-22)` (태그 표기)
  * `- [ ] 선물 주문 (마감: 9월 25일)` (한글 구어체 표기)
* **대화형 마감일 태스크 생성**:
  * "다음 주 수요일까지 자동차 검사 예약 gtd에 넣어줘" ➔ 날짜 계산 후 `- [ ] 자동차 검사 예약 ~2026-09-24`로 등록.
* **아침 브리핑 D-Day 경고 섹션 신설**:
  * 아침 08:30 브리핑 상단에 긴급 일정 하이라이트:
    * 🚨 **오늘 마감 (D-Day)**: 즉시 수행해야 할 최우선 과제
    * ⚠️ **마감 임박 (D-1 ~ D-3)**: 곧 마감되는 과제
    * ⛔ **기한 초과 (Overdue)**: 이미 마감일이 지난 방치 과제 경고
* **정렬 알고리즘 고도화**:
  * Next Actions 조회 및 원클릭 태스크 완료 시 마감일이 임박한 순서대로 우선 정렬.

#### 3) 기술 아키텍처 설계
* `DateParserService`:
  * 한국어 상대 일자("오늘", "내일", "모레", "이번 주 금요일", "다음 주 화요일") 및 정규식 날짜 파서 구축.
* `BriefingService` 연동:
  * 브리핑 생성 시 Next Actions 및 Inbox 파일의 각 태스크에서 마감일을 추출하고 현재 일자(KST)와의 차이(`d_day`)를 계산하여 그룹핑.

### 아이디어 4: [웹 경험 혁신] 웹 대시보드 연간 잔디(Heatmap) & 마크다운 인플레이스 에디터
> **"웹 대시보드에서 매일의 기록 현황을 깃허브 잔디로 확인하고, 마크다운 파일을 분할 화면에서 바로 수정"**

#### 1) 배경 및 필요성
* 웹 콘솔(`/watson`)은 채팅 중심 인터페이스로 구성되어 있어, 내가 얼마나 성실하게 일기를 썼는지 시각적인 성취감을 느끼기 어렵습니다.
* 또한 오탈자 수정이나 복잡한 일기 서식 편집은 챗봇 대화보다 **직관적인 마크다운 에디터**가 훨씬 편리합니다.

#### 2) 주요 기능 명세
* **라이프로그 연간 잔디 (Contribution Heatmap)**:
  * 웹 대시보드 상단 또는 사이드바에 GitHub 스타일의 일일 기록 잔디(최근 6개월~1년) 렌더링.
  * 각 날짜 셀을 호버/클릭하면 작성된 글자 수, 완료한 태스크 개수, 커밋 수 표시.
  * 특정 날짜 클릭 시 해당 일자의 일일 로그(`YYYY-MM-DD.md`)로 즉시 이동.
* **마크다운 인플레이스 분할 에디터 (Split View Editor)**:
  * 좌측: 마크다운 텍스트 편집기 (코드 블록, 체크박스 지원).
  * 우측: 실시간 렌더링 프리뷰 (체크박스 토글 가능).
  * 상단: `[💾 저장 및 원격 커밋/푸시]` 버튼으로 수동 수정 즉시 Git 원자적 반영.
* **캘린더 뷰 & 날짜별 탐색기**:
  * 월별 달력에서 일기가 작성된 날에 점(Dot)을 표시하고, 과거 기록을 날짜 클릭으로 편하게 서핑.

#### 3) 기술 아키텍처 설계
* `HeatmapService`:
  * `GET /api/lifelog/heatmap`: 최근 365일간의 날짜별 기록 유무, 단어 수, 커밋 수 JSON 반환 (캐싱 적용).
* 경량 프론트엔드 컴포넌트:
  * 외부 무거운 라이브러리 없이 순수 SVG/CSS Grid 기반 경량 히트맵 렌더러 구현.
  * `marked.js` + 심플 텍스트에어리어 기반 인플레이스 에디터 모달.

## 2. 👥 다른 사람도 쓸 수 있게 만드는 방법 (Multi-User & Distribution Strategy)

왓슨을 본인뿐 아니라 가족, 동료, 혹은 일반 사용자들도 손쉽게 자신의 비서로 쓸 수 있게 하려면 어떤 전략이 필요할까요?

### 💡 핵심 고려사항 (Challenges)
1. **극도의 개인정보 보호 (Privacy & Confidentiality)**:
   * 라이프로그와 GTD는 **개인의 일기, 감정, 건강, 금융, 가족사**가 담긴 초민감 데이터입니다.
   * 타인의 데이터가 섞이거나 유출되는 일은 절대 없어야 합니다.
2. **독립적인 저장소 소유권 (Data Ownership)**:
   * 사용자는 서비스 제공자가 아니라 **자신의 개인 GitHub 레포지토리**에 마크다운이 저장되기를 원합니다.
3. **개인별 통신 채널 분리**:
   * 각자 자신의 텔레그램 계정(Chat ID)으로 자신의 비서와 1:1 대화를 나누어야 합니다.

### 접근법 A: [1-Click 셀프호스팅 템플릿] 프라이버시 중심 개인화 배포 (추천 ⭐️)
> **"GitHub 템플릿 클릭 ➔ 배포 스크립트 1회 실행 ➔ 10분 만에 나만의 비서 완성"**

* **컨셉**:
  * 사용자가 자신의 서버(오라클 클라우드 무료 인스턴스, 라즈베리 파이, 개인 VPS, 홈 서버)에 왓슨을 직접 띄우는 방식.
* **장점**:
  * **보안 & 신뢰 100%**: 데이터가 제3자 서버를 거치지 않고 오직 사용자의 기기와 GitHub 레포에만 보존.
  * **운영 비용 제로**: 서비스 운영자가 서버비나 API 비용을 대납할 필요 없음.
* **구체적 구현 방안**:
  1. **GitHub Repository Template 화**:
     * `watson-bot` 레포를 Template으로 공개하여 누구나 `Use this template` 버튼 클릭 한 번으로 포크.
  2. **대화형 셋업 위저드 (`./scripts/setup_wizard.sh`) 제공**:
     * 터미널에서 스크립트를 실행하면 왓슨 비서가 대화식으로 질문:
       * "텔레그램 봇 토큰을 입력해주세요:"
       * "본인의 텔레그램 ID를 입력해주세요:"
       * "GTD 저장소 경로를 입력해주세요:"
       * "거주하시는 동네명을 입력해주세요 (예: 성동구 금호동):"
     * 입력값을 기반으로 `.env`, `commute_config.json`, Cloudflare Tunnel을 자동 설정하고 systemd 서비스 또는 Docker Compose로 원클릭 가동.
  3. **초보자를 위한 완벽 가이드 문서**:
     * 오라클 클라우드 Always Free(평생 무료) VM 생성부터 텔레그램 봇 발급, 실행까지 스크린샷이 포함된 친절한 가이드 제공.

### 접근법 B: [멀티테넌트(Multi-Tenant) SaaS형 아키텍처] 단일 봇 기반 다중 사용자 서비스
> **"웹사이트에서 회원가입 후 텔레그램 봇 시작만 누르면 즉시 개인 비서가 되는 형태"**

* **컨셉**:
  * 왓슨 서버 1대로 수십~수백 명의 사용자가 동시에 자신만의 GTD와 일기를 기록할 수 있는 클라우드 서비스 구조.

```text
[ 유저 A (텔레그램) ] ──┐
[ 유저 B (텔레그램) ] ──┼──> [ 단일 텔레그램 봇 / Webhook ]
[ 유저 C (웹 콘솔)  ] ──┘                 │
                                          ▼
                            [ Tenant Router & Auth Guard ]
                                (chat_id / Session 매핑)
                                          │
                   ┌──────────────────────┼──────────────────────┐
                   ▼                      ▼                      ▼
           [ User A Context ]     [ User B Context ]     [ User C Context ]
           - GitHub Token A       - GitHub Token B       - GitHub Token C
           - Repo A (/data/A)     - Repo B (/data/B)     - Repo C (/data/C)
           - 동네: 성동구          - 동네: 분당구          - 동네: 강남구
           - 브리핑: 08:30        - 브리핑: 07:45        - 브리핑: 09:00
```

#### 1) 핵심 아키텍처 요구사항
1. **사용자 계정 & 테넌트 데이터 격리 (`Tenant Isolation`)**:
   * SQLite / PostgreSQL에 `users` 테이블 신설:
     * `user_id`, `email`, `hashed_password`, `telegram_chat_id`, `timezone`
     * `github_repo_url`, `github_pat_encrypted` (Fernet 양방향 암호화)
   * 디스크 저장소 격리:
     * `/data/tenants/{user_id}/gtd/` 경로에 각 사용자의 독립 Git 레포지토리 클론.
2. **텔레그램 다중 사용자 라우터 (`Telegram Multi-User Dispatcher`)**:
   * 봇 메시지 인입 시 `update.message.from_user.id`로 사용자 DB 조회.
   * **신규 사용자 온보딩 UX**:
     * 등록되지 않은 사용자가 `/start` 전송 시: "반갑습니다! 왓슨 비서입니다. 서비스를 시작하려면 발급받으신 연동 코드 6자리를 입력하시거나, 웹 대시보드(https://...)에서 계정을 생성해주세요."
     * 원클릭 딥링크 지원: `https://t.me/watson_bot?start=LINK_TOKEN_12345`
3. **사용자 자격증명 암호화 금고 (`Security & Vault`)**:
   * 사용자의 GitHub Personal Access Token(PAT), 기상청/공공데이터 API 키를 AES-256 (Fernet)으로 암호화하여 DB 보관.
   * Git 작업 수행 시 메모리 상에서만 복호화하여 일시적 인증에 사용 후 소거.
4. **동적 다중 스케줄러 (`Dynamic Multi-User Briefing Scheduler`)**:
   * 단일 고정 시간(08:30) 발송 대신, 사용자별로 설정된 출근 시각과 브리핑 시각에 맞춰 큐(APScheduler)를 통해 개별 푸시 발송.
   * A 사용자는 07:30 성동구 금호동 브리핑, B 사용자는 08:00 분당 판교동 브리핑 동적 실행.

> 3. **3단계**: 이후 대중적인 배포 수요가 커지면 **`접근법 B (멀티테넌트 아키텍처)`**로 점진적 확장을 검토합니다.
